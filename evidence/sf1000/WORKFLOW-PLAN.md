## Facts established before the analysis
1. FE StatisticsCalculator.computeFileScanNode sets outputRowCount = 1 for FILES() scans ("we don't know the real schema in file, just use the default Row Count now"); every column statistic UNKNOWN. Hence every plan node has cardinality 1 and the CBO picks BROADCAST for most joins (orders 1.5B rows broadcast in q07/q09/q10..., lineitem 3.79B rows as the build side of q04's LEFT SEMI JOIN, partsupp 800M in q02).
2. Engine stream ids == FE exchange node ids; the receiver declares the exact parked row count per stream before build() ("declared input stream cardinality"), so DuckDB plans the receiver fragment with exact input cardinalities, but only after every sender finished (receiver-first rendezvous, local_exchange.rs). Nothing streams across a fragment boundary: the whole intermediate is parked on the GPU.
3. Engine OOM handling: gpu_pipeline_executor.cpp reschedules a task on OOM up to MAX_RETRIES=100 with a 50 ms sleep, then fails the query ("exceeded maximum retry limit"). It does not wait for memory to be released and cannot spill parked batches. q05 and q08 died this way on 1 CN at SF1000 (GPU_SCAN OOM, 101 s and 168 s).
4. Reserving.requested_bytes / peak_estimate vs Computing.peak_allocated_bytes (Quent task FSM) measure the engine's own memory estimation; standalone SF10 q01 requested 20.8 GB for a 5.6 GB peak.

## Analysis dimensions (workflow)
A. Planning: per query, FE fragment tree and join distribution vs the DuckDB/Sirius standalone plan; what a stats-aware FE would choose; where the translator/CN could override (e.g. swap build/probe, refuse broadcast above a row threshold, local re-planning of a broadcast join once the actual parked cardinality is known).
B. Cardinality: FE estimate vs actual rows per exchange (card_compare), engine reservation estimate vs peak (quent_bp), the receiver-first exact-cardinality mechanism and its cost.
C. Backpressure: parked bytes and dwell per fragment, staging lease held/in-transit time and max concurrency vs SIRIUS_EXCHANGE_STAGING_BYTES, Reserving/Queued waits, OOM reschedule storms, nixl transmit lease_ms/write_ms, 1-CN vs 4-CN scaling per query, standalone vs CN.
Each per-query analysis is verified adversarially (two skeptics with different lenses); the synthesis ranks findings with the evidence lines and proposes changes with file paths and confidence.

CORRECTION to fact 6: the A/B in fact 20 REFUTES the simple hypothesis that the SIRIUS_CANONICAL_FLOAT_SUMS gate alone explains q15's empty runs: with the canonical sort ON, 4 of 6 runs still return 0 rows (gate off: 5 of 6). The gate only canonicalizes row order inside the update-phase aggregate; the FE plan computes the revenue CTE twice (two independent two-phase aggregations over FP64-lowered decimals) and then joins on `total_revenue = max(total_revenue)`. Batch arrival order into the merge phase (and therefore FP64 summation order) still varies run to run, so the two sums can differ in the last bits and the equality join yields nothing. Standalone Sirius keeps DECIMAL and returns the row every time. Treat this as a correctness finding about equality joins on FP64-lowered aggregates on the CN path; verify from cn1-canon-q15/ and cn1-nocanon-q15/ logs (declared cardinalities of streams 18/22 per run) and the translator's decimal->FP64 lowering (#1236, cast_to_fp64 in expr_translator.rs).
